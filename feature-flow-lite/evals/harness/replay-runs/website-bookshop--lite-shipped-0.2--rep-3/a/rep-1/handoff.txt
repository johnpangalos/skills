ACCEPTANCE CRITERIA:
1. index.html, books.html, events.html, visit.html exist at the repo root. Each has `<html lang="en">`, a unique descriptive `<title>`, a meta viewport, one `<h1>`, landmarks (`header`, `nav` with an accessible name, `main`, `footer`), and a skip link as the first focusable element that moves focus to `main`.
2. Shared nav on every page links all four pages in the same order; the current page's link has `aria-current="page"`. On narrow screens the nav may collapse behind a real `<button>` with `aria-expanded` and `aria-controls` that toggles it; Escape closes it and returns focus to the button; the menu is reachable and operable by keyboard alone. Hostile: open menu then resize to desktop (nav must still be visible/usable); repeated rapid toggles; Tab past the last menu item.
3. Home page: introduces the shop (who they are, what makes them different), with sections linking to books, events and visit, and a short preview of upcoming events or featured books with real content.
4. Books page: a catalog of at least 12 fictional titles (spec floor is 8; make the filter worth using), each with title, author, genre, price, and a short description; at least 5 genres, each with 2+ books. A genre filter (a labelled `<select>` or a group of buttons with `aria-pressed`, or radio buttons in a fieldset with a legend) narrows the list to that genre; "All genres" shows every book. A live region announces the result count (e.g. "Showing 3 of 12 books"). Genre options are generated from the data, so no option is ever empty.
   Hostile inputs: URL `books.html?genre=poetry` loads with that filter applied and the control reflecting it; `?genre=unknown-thing`, `?genre=`, `?genre=<script>alert(1)</script>`, and a mixed-case `?genre=POETRY` fall back gracefully (unknown → All, shown as All, no injected HTML, no console error); changing the filter updates the URL (history.replaceState or pushState) and, if pushState is used, Back/Forward restore the filter and the control.
5. Events page: at least 5 events, each with title, date and time (in a `<time datetime>` element), short description, and a note on whether booking is needed. Events are listed in date order. Which events are upcoming vs past is decided by the visitor's local date at load: events on today's date count as upcoming; past events are hidden or shown in a separate, clearly labelled "Past events" section. Make most event dates in 2027 so the page stays useful, but include at least one past event (e.g. in 2026 before November) so the past logic is exercised. If no upcoming events remain, show a plain message instead of an empty list. Hostile: an event dated today (local) — must be upcoming, test by mocking the clock (Playwright `page.clock.setFixedTime` or overriding Date) late at night e.g. 23:30 local; a clock set after every event — must show the "no upcoming events" message.
6. Visit page: opening hours for each day of the week in a semantic table or description list, the full (fictional) street address in an `<address>` element, phone and email as links (tel:/mailto:), directions/access notes, and a contact form.
7. Contact form: name, email, subject or topic, and message fields, each with a visible `<label>`; required fields marked in text, not color alone. Validation on submit in JS (use `novalidate` and do your own): empty required fields, malformed email (e.g. `a@`, `@b.com`, `a b@c.com`, whitespace only) are rejected with a specific error message next to each field, linked via `aria-describedby`, `aria-invalid="true"` set, and focus moved to the first invalid field (or to an error summary). Errors clear when corrected. A message over a sane max length (e.g. 2000 chars) is rejected or prevented with a visible counter. On valid submit the form must NOT claim a message was sent: there is no backend, so show a clear status (in a live region) saying this is a demo and nothing was sent, and point to the email/phone. The page must state the form is a demo before the user submits, too. Submitting never navigates away or reloads. Hostile: whitespace-only name/message; double submit; pasting 10,000 characters.
8. Responsive: on every page at 360px viewport width, `document.documentElement.scrollWidth <= 360` (no sideways scroll), text is not clipped, and touch targets for nav and filter controls are at least 44px high. Also looks right at 768px and 1280px.
9. Accessible: visible focus indicator on every interactive element (do not remove outlines without replacement); text color contrast at least 4.5:1 (state the palette in CSS custom properties); images/SVGs either have alt text or are `aria-hidden` if decorative; headings in order without skipped levels; respects `prefers-reduced-motion`; no element that looks clickable but isn't.
10. No external network requests: loading each page in headless Chrome, every request's origin is the local server's origin. No `http://` or `https://` URLs in src/href attributes pointing elsewhere (mailto:/tel: are fine).
11. No console errors or uncaught exceptions on any page.
12. README.md describes the site and how to run it locally (`npx http-server .` or `python3 -m http.server`) and how to run the tests and lint.
13. Tests in `tests/` load the pages in headless Chrome via Playwright from a local static server started by the tests (pick a free port), and cover criteria 1, 2, 4 (including every hostile URL), 5 (with a mocked clock), 7 (each hostile input), 8 (360px on every page), 10 and 11.
