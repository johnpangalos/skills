ACCEPTANCE CRITERIA:
- shop/orders.py defines RefundError (subclass of ValueError), place_order(cart) -> Order, refund(order, amount, key) -> Refund.
- place_order snapshots cart.total(): order.total equals cart.total() at placement and does not change if the cart is modified afterwards.
- Every order gets a unique id; two orders placed from the same cart have different ids.
- Placing an order from an empty cart raises ValueError (and returns no order). Hostile: cart emptied by remove() after adding.
- order.refunded() is the sum of its refunds (Decimal("0.00") when none); order.refundable() is total minus refunded().
- amount must be a Decimal greater than zero in whole cents; anything else raises RefundError (never TypeError, decimal.InvalidOperation or any other exception type). Hostile: float 5.0, int 5, str "5.00", bool True, None, Decimal("0"), Decimal("-0"), Decimal("-1.00"), Decimal("0.001"), Decimal("1.005"), Decimal("NaN"), Decimal("sNaN") (comparing sNaN raises InvalidOperation — check is_finite() first), Decimal("Infinity"), Decimal("1E+40") (quantize can raise InvalidOperation for huge values). Decimal("5") and Decimal("5.000") are whole cents and valid.
- Refunds can be partial; multiple refunds may sum to exactly the total; a refund that would push refunded() above total raises RefundError and changes nothing (refunded(), the recorded refunds, and the key are all unchanged, so the same key can later be used with a valid amount). Hostile: refund exactly total (ok), total + 0.01 (fails), partials summing to total then 0.01 more (fails).
- key is an idempotency key scoped to its order: refund(order, same amount, same key) returns the original Refund object (same instance) and refunded() doesn't change; equal-valued amounts count as the same (Decimal("5") vs Decimal("5.00")). Same key with a different amount raises RefundError and changes nothing. Hostile: retry of a refund that fully refunded the order still returns the original (idempotency check happens before the cap check); the same key on two different orders creates two independent refunds; a key from a failed refund is not recorded.
- A Refund records order_id, amount and key (attributes with those names).
- Tests in tests/test_orders.py cover each criterion above, including the hostile inputs; README.md mentions orders/refunds; ./check.sh passes.

Extra probes worth trying: Decimal subclasses; amounts with 30+ significant digits (default context precision is 28 — does `refunded() + amount > total` round so an over-refund slips through?); a non-default decimal context (e.g. decimal.localcontext with prec=3 or traps on Inexact) during refund; key=None; unhashable key.
