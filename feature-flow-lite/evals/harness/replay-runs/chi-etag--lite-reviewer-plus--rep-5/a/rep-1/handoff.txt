ACCEPTANCE CRITERIA:
1. `middleware.ETag(next http.Handler) http.Handler` exists in `middleware/etag.go` with a doc comment (says it buffers whole GET/HEAD responses in memory, so it is unsuited to large or streamed responses, and that If-None-Match uses weak comparison). Tests live in `middleware/etag_test.go`. No new dependencies.
2. GET and HEAD: the response is buffered. If the final status is 200 (explicit `WriteHeader(200)` or implicit via first `Write`, or no write at all) and the handler did not set an `ETag` header, the middleware sets `ETag` to a strong entity tag computed from the buffered body: double-quoted, no `W/` prefix, only hex chars inside the quotes (e.g. `"` + hex of a sha256/truncated hash + `"`). Same body -> same tag; different body -> different tag; empty body still gets a tag. The body and all other headers the handler set are delivered unchanged.
   - Hostile: handler writes nothing at all; handler writes in many small chunks (tag equals the tag of the concatenated body); body of several MB.
3. A handler-set `ETag` (strong or weak, e.g. `W/"v1"`) is never overwritten or altered.
4. If-None-Match: for a 200 GET/HEAD response, if any member of the request's If-None-Match matches the response ETag under RFC 9110 weak comparison (opaque-tags equal, `W/` ignored on either side), or the field value is `*`, respond `304 Not Modified` with an empty body instead. The 304 keeps the `ETag` header and other headers (Cache-Control, Vary, Date, Expires, Content-Location), and drops `Content-Type`, `Content-Length` and `Content-Encoding` (as net/http's ServeContent does). All If-None-Match header lines are considered (`r.Header.Values`). Comma-separated lists with optional whitespace (`"a" , W/"b",  "c"`) are parsed.
   - Hostile: `W/"x"` request vs strong `"x"` response and vice versa -> 304; `"x"` vs `"xy"` or `"X"` -> 200 (no prefix/case match); empty or whitespace-only If-None-Match -> 200; malformed members (unquoted `abc`, unterminated `"abc`, `W/abc`, stray commas `,,`) never produce a match and never panic — follow net/http's checkIfNoneMatch behavior (skip empty members, stop at a malformed one); `*` mixed into a list is not special unless it is the whole value; a handler-set unquoted (malformed) ETag `abc` does not match request `"abc"`.
5. Other methods (POST, PUT, DELETE, PATCH, OPTIONS, ...) pass through unchanged: the handler gets the original ResponseWriter, nothing is buffered, no ETag is added, and If-None-Match is ignored (no 304).
6. Non-200 final statuses (201, 204, 206, 301, 404, 500, ...) on GET/HEAD pass through unchanged: same status, headers and body, no ETag added, no 304 even if If-None-Match is `*` or matches a handler-set ETag. 1xx informational WriteHeader calls (e.g. 103) are forwarded immediately and do not fix the final status. A second WriteHeader call is ignored, like net/http.
7. The wrapping writer forwards optional capabilities like `compressResponseWriter` in middleware/compress.go: `Flush` (calling it stops buffering: commits the status and headers as they stand — no computed ETag, no 304 — writes the buffered bytes, flushes the underlying writer if it can, and later writes stream straight through), `Hijack` and `Push` (forwarded, or return a `chi/middleware: ...` error when the underlying writer lacks them), and `Unwrap() http.ResponseWriter` so `http.NewResponseController` works.
8. HEAD: same ETag and 304 behavior as GET; the tag for HEAD is computed from whatever the handler wrote (net/http discards a HEAD body itself).
9. No shared mutable state between requests; tests pass under `-race`, including a test that serves concurrent requests.
