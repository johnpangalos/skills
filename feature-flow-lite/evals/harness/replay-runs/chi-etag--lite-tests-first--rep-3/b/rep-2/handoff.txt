ACCEPTANCE CRITERIA:
1. `middleware.ETag` has type `func(http.Handler) http.Handler` and is usable as `r.Use(middleware.ETag)`.
2. GET or HEAD, handler responds 200 (explicit WriteHeader(200) or implicit via Write, or writes nothing at all) and sets no ETag → response carries a strong ETag `"<hex digest>"` (quoted, no `W/`) computed from the full body (e.g. SHA-256, may be truncated but ≥ 64 bits); same body → same ETag; different body → different ETag; body bytes and other headers reach the client unchanged.
   Hostile: body written in many small Writes or via io.Copy/ReadFrom must give the same ETag as one Write; empty body on GET still gets the ETag of the empty body.
3. HEAD: when the handler writes the body (as GET handlers do via GetHead), ETag equals the GET ETag and no body is sent. When a HEAD handler writes no body bytes, no ETag is generated (omitting beats a wrong one); a handler-set ETag is still used.
4. Handler already set `ETag` (strong or weak, via Header().Set before WriteHeader/Write) → that value is left exactly as is, never replaced.
5. If-None-Match matches the response ETag (generated or handler-set) on a 200 GET/HEAD → 304 with no body; ETag, Cache-Control, Vary, Expires, Content-Location, Date and other headers kept; Content-Type, Content-Length, Content-Encoding removed, and Last-Modified removed (as net/http writeNotModified does). Otherwise the 200 response is sent normally.
6. Matching per RFC 9110 §13.1.2: weak comparison (`W/"x"` matches `"x"` either way round; opaque-tag must be equal); comma-separated lists with optional whitespace (spaces/tabs) and empty members (`, ,"a"`); multiple If-None-Match header lines are all considered; `*` matches any 200 response.
   Hostile: `"a","b"` with no spaces; malformed members (`abc`, `"unterminated`, `W/abc`) never match and never panic; header that is empty or only whitespace/commas → no 304; a tag that is a prefix/substring of the ETag (`"ab"` vs `"abc"`) does not match; If-None-Match case-insensitivity doesn't apply to tags (`"ABC"` ≠ `"abc"`); a handler-set ETag that isn't a valid entity-tag only matches `*`.
7. Methods other than GET/HEAD (POST, PUT, DELETE, OPTIONS…) pass straight through: no buffering, no ETag added, If-None-Match ignored, Flush/Hijack behave as without the middleware.
8. Non-200 final statuses (201, 204, 206, 301, 304 from the handler, 404, 500…) pass through unchanged: status, headers and body exactly as the handler produced them, no ETag added, no 304 conversion. Once a non-200 status is known, writes and Flush go straight to the underlying writer (streaming works).
   Hostile: handler calls WriteHeader twice (second ignored as net/http does, no panic); handler writes body before WriteHeader (implicit 200 wins).
9. 1xx informational statuses (e.g. WriteHeader(103) with a Link header) are forwarded immediately and do not count as the final status; a later 200 is still buffered and ETagged.
10. Writer capabilities, following compress.go: `Flush` is implemented (no-op while buffering a 200; forwards once passing through); `Hijack` and `Push` forward to the underlying writer or return the compress.go-worded errors; `Unwrap` returns the underlying writer so `http.NewResponseController` works. Test that wrapping a writer without Hijacker yields the error, and that ResponseController.Flush during a buffered 200 doesn't send a partial response.
11. Header changes the handler makes after WriteHeader/first Write do not reach the client (same as without the middleware), including an ETag set late.
12. If the handler panics, the middleware writes nothing and the panic propagates (Recoverer outside it still produces its 500).
13. Concurrent requests through the same middleware are race-free under `-race`.

TRIGGERED CHECKS:
## Invariants, round trips and equivalence

- **Trigger:** the criteria state something that must always hold (a balance never negative,
  a total never over a cap), a round trip (parse then format, encode then decode), idempotency
  (doing it twice equals doing it once), or that new code must match old code.
- **Check:** a property test. Use the repo's property library if it has one (Hypothesis,
  fast-check, proptest); otherwise a seeded random loop of at least 1000 generated inputs,
  including the hostile ones, that asserts the property and prints the first failing input.
- **From:** edge cases that the implementor's own tests missed because the tests shared the
  code's assumptions.

## Wrappers and stand-ins

- **Trigger:** the new code wraps or replaces something: a response writer, stream, handler,
  middleware, file, parameter type, DOM node.
- **Check:** a differential test. Run the same inputs through the wrapped and the unwrapped
  version, across call orders (before and after the first write, flush, hijack, close, a
  second call), and diff every output: status, headers, body, errors, side effects. The
  handoff's `APPROVED DIFFERENCES:` lists what the request changes on purpose. A difference
  not on that list is [blocking]. So is an approved difference that doesn't actually happen:
  check each one directly, in every call order.
- **From:** a buffering response writer whose Flush still sent bytes early, which the request
  ruled out; probes that compared only pass-through behaviour couldn't see it.

## Nesting and composition

- **Trigger:** the code walks a tree or a container (DOM, shadow roots, portals, slots,
  routers, nested config), or the thing it builds can contain another of itself.
- **Check:** nest it. Put a target inside another target, including inside another target's
  shadow root; a dialog in a dialog; a router mounted in a router. Check the inner and the
  outer each still behave as they do alone, and that nothing inside a target gets the
  treatment meant for what's outside it.
- **From:** hide-everything-else logic that walked into a nested target's shadow root, and
  dialogs where one Escape closed both.

## HTTP responses

- **Trigger:** the change sets or computes response headers, status or body (caching,
  compression, ETags, content length, streaming).
- **Check:** probe HEAD, a conditional request that should return 304, an empty body, a
  response streamed across several writes, headers set after the first write, and an error
  status. Each gets the headers its method and status call for; a HEAD response never carries
  a validator computed from an empty body.
- **From:** ETags computed from the empty body of HEAD responses.
