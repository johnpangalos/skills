ACCEPTANCE CRITERIA:
1. `func ETag(next http.Handler) http.Handler` exists in middleware/etag.go with a doc comment.
2. GET/HEAD, handler responds 200 (explicit WriteHeader(200) or implicit via first Write) with no ETag header: response has a strong ETag `"<token>"` (double-quoted, no `W/`, only etagc characters) derived from the body; identical bodies give identical ETags, different bodies give different ETags. Body and status reach the client unchanged.
   Hostile: empty body (still gets a valid ETag on GET); body written in many small Write calls (same ETag as one Write of the same bytes); handler that writes the body and never calls WriteHeader.
3. Handler-set ETag (strong or weak, e.g. `W/"v1"`) is kept as-is, never overwritten.
4. If-None-Match matches the response's ETag (computed or handler-set) on a GET/HEAD 200 → status 304, empty body, ETag header kept, other headers like Cache-Control/Vary/Expires kept, and Content-Type, Content-Length, Content-Encoding removed (as net/http's writeNotModified does). No match → normal 200 with body and ETag.
5. Matching per RFC 9110 §13.1.2 with weak comparison: `W/"x"` matches `"x"` and vice versa in either header; comma-separated list with optional whitespace (`"a", W/"b" ,"c"`); empty list members (`"a",,"b"`) tolerated; multiple If-None-Match header lines are all considered; `*` alone matches any 200 response.
   Hostile: unquoted `abc` must not match ETag `"abc"`; unterminated `"abc` must not match and must not panic; empty header value → no 304; `W/` without a quoted tag → no match, no panic; an ETag value containing a comma inside quotes is compared as one tag (`"a,b"`).
6. HEAD: if the handler writes the body (Go discards it), the ETag equals GET's. If a HEAD handler writes no body but set a non-zero Content-Length, do NOT emit a computed ETag (can't be right) — but a handler-set ETag still drives 304 matching.
7. Other methods (POST, PUT, DELETE, PATCH, OPTIONS…) are not buffered at all: `next` is called with the original ResponseWriter (no ETag, no 304 even if If-None-Match matches).
8. Non-200 responses on GET/HEAD (201, 204, 206, 301, 304 from the handler, 404, 500…) pass through unchanged: same status, headers, body; no ETag added; no 304 substitution even if If-None-Match matches a handler-set ETag.
9. Wrapper forwards optional interfaces like compress.go: `Unwrap()` returns the original writer (so http.NewResponseController works); `Hijack` and `Push` forward or return the chi/middleware error; on Flush the wrapper commits buffered status/headers/body WITHOUT a computed ETag, flushes the underlying writer, and passes later writes straight through. A test covers streaming via Flush.
10. WriteHeader called twice: the first status wins; 1xx informational codes are passed straight through and don't fix the final status.
11. Tests in middleware/etag_test.go cover every criterion and hostile input above.
12. README "Core middlewares" table has an ETag row and the `[ETag]:` pkg.go.dev link.
13. Standing: `go test -race ./...`, `go vet ./...` pass and `gofmt -l .` prints nothing; no new dependencies.

TRIGGERED CHECKS:
## Invariants, round trips and equivalence

- **Trigger:** the criteria state something that must always hold (a balance never negative,
  a total never over a cap), a round trip (parse then format, encode then decode), idempotency
  (doing it twice equals doing it once), or that new code must match old code.
- **Check:** a property test. Use the repo's property library if it has one (Hypothesis,
  fast-check, proptest); otherwise a seeded random loop of at least 1000 generated inputs,
  including the hostile ones, that asserts the property and prints the first failing input.
- **From:** edge cases that the implementor's own tests missed because the tests shared the
  code's assumptions.

## Wrappers and stand-ins

- **Trigger:** the new code wraps or replaces something: a response writer, stream, handler,
  middleware, file, parameter type, DOM node.
- **Check:** a differential test. Run the same inputs through the wrapped and the unwrapped
  version, across call orders (before and after the first write, flush, hijack, close, a
  second call), and diff every output: status, headers, body, errors, side effects. The
  handoff's `APPROVED DIFFERENCES:` lists what the request changes on purpose. A difference
  not on that list is [blocking]. So is an approved difference that doesn't actually happen:
  check each one directly, in every call order.
- **From:** a buffering response writer whose Flush still sent bytes early, which the request
  ruled out; probes that compared only pass-through behaviour couldn't see it.

## Nesting and composition

- **Trigger:** the code walks a tree or a container (DOM, shadow roots, portals, slots,
  routers, nested config), or the thing it builds can contain another of itself.
- **Check:** nest it. Put a target inside another target, including inside another target's
  shadow root; a dialog in a dialog; a router mounted in a router. Check the inner and the
  outer each still behave as they do alone, and that nothing inside a target gets the
  treatment meant for what's outside it.
- **From:** hide-everything-else logic that walked into a nested target's shadow root, and
  dialogs where one Escape closed both.

## HTTP responses

- **Trigger:** the change sets or computes response headers, status or body (caching,
  compression, ETags, content length, streaming).
- **Check:** probe HEAD, a conditional request that should return 304, an empty body, a
  response streamed across several writes, headers set after the first write, and an error
  status. Each gets the headers its method and status call for; a HEAD response never carries
  a validator computed from an empty body.
- **From:** ETags computed from the empty body of HEAD responses.
